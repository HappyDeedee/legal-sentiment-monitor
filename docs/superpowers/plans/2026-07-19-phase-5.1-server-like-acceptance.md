> packet serially. This is an evidence and operations packet. If a product
> defect is found, stop, register a follow-up regression CR, fix it in a
> separate atomic package, merge and reverify it, then restart this acceptance
> from the affected checkpoint.

**Goal:** Prove that the merged CR-047 account identity implementation works
through a real server-controlled browser, real platform login/check/crawl,
real account-bound proxy egress, persistent Profile restart, and all formal
run triggers without generic Profile, process-proxy, connect-existing CDP, or
standard-browser fallback.

**Architecture:** Add a redacted evidence contract and checker, then execute a
dedicated acceptance deployment at the exact merged commit. Automated tests
remain synthetic and side-effect free. Real evidence is collected only from a
dedicated operator-approved account/proxy/deployment and is reduced to safe
booleans, digests, timestamps, and internal record references before it enters
project documentation.

**Tech Stack:** Python 3.11, FastAPI, SQLite, Playwright 1.45.0, launch-owned
Chromium CDP, Docker Compose or Linux systemd, existing monitor UI/API/CLI and
scheduler, pytest.

## Confirmed Acceptance Decisions

1. **Deployment authority.** Final evidence comes from a Linux container or
   Linux systemd service that owns the browser and persistent Profile. Docker
   Compose is preferred. A Windows isolated service may be used only for local
   preflight.
2. **Platform breadth.** One real monitor-supported platform is sufficient for
   the end-to-end external workflow because the standard suite proves all
   seven adapters. The evidence names only a safe platform code and redacted
   account reference.
3. **Two account fixtures.** The QR account proves persistent Profile login,
   restart, Profile check, and crawl. A separate Cookie account proves the
   current ephemeral Cookie-validation path without claiming CR-112 durable
   promotion.
4. **Trigger breadth.** The QR account runs one bounded job serially through
   HTTP manual, scheduler, and monitor CLI triggers. Each trigger must produce
   its own safe runtime result while preserving the same stable environment
   digest. Runs use a narrow keyword/range and remain low concurrency.
5. **Proxy proof.** At least the QR account uses a non-null account proxy. The
   browser-routed probe must return the exact safe region before platform work.
   Requested proxy metadata, an HTTP-client-only check, or a default-network
   success does not pass.
6. **Profile proof.** Acceptance records a safe digest derived from the stable
   environment fields and Profile identity, not a raw Profile path. The
   service/browser restarts, then Profile check and a later crawl must use the
   same digest and remain logged in.
7. **Fallback proof.** Safe runtime results must show the managed provider,
   launch-owned mode, exact account/profile reference, proved proxy policy,
   browser source, no mismatch evidence, and `fallback_used=false`. These
   persisted safe fields, together with successful child-result validation
   before ingest, are the formal proof that generic Profile, process-proxy
   fallback, connect-existing CDP, and standard fallback were not accepted.
   Raw process argv/environment inspection is optional diagnosis and cannot be
   required, stored, or used to upgrade incomplete evidence.
8. **Evidence boundary.** The committed repository contains only the checker,
   an incomplete synthetic example, tests, and summarized `TEST_RESULTS.md`
   outcome. Filled real evidence, logs, screenshots, database copies, Cookies,
   proxy endpoints, Profile files, and environment files stay outside Git.
9. **No acceptance-time patching.** A runtime failure or missing invariant is
   evidence of an open defect, not a reason to modify code in this packet. A
   separate regression CR must merge before the failed checkpoint is rerun.
10. **Completion semantics.** The packet is complete only when every required
    evidence field passes the checker and the operator/reviewer attest that
    referenced actions were observed. The checker proves schema completeness,
    chronology, internal consistency, and redaction; it does not independently
    authenticate an external platform action. `blocked`, partial, mocked,
    local-only, or operator-unconfirmed evidence keeps Phase 5.1 and CR-070
    visibly open.

## Evidence Contract

Add `scripts/phase_5_1_acceptance_evidence.py` with schema
`phase_5_1_acceptance_v1`. The generated template begins with
`status=incomplete`. The checker accepts `status=passed` only when these groups
are complete:

  timestamps in valid chronological order;
- service and web administrator login succeeded;
- server-owned browser source/family/version observed;
- persistent data and Profile roots mounted;

- connect-existing CDP disabled;
- service/container restart completed.

### Account And Login Matrix

- Cookie account safe reference and platform code;
- QR returned through web UI and ordinary operator verification completed;
- QR account-level validation locked/activated the identity;
- Cookie validation completed under its own managed environment;
- post-restart QR Profile check remained logged in;
- each action has a safe runtime-result reference and matching stable
  environment digest, unique resolution/attempt reference, action, and trigger
  source;
- QR account environment lock timestamp and digest are recorded before restart
  and remain unchanged after restart.

### Proxy And Effective Runtime

- QR account has non-null account proxy binding;
- browser-routed region proof passed before platform work;
- requested/effective required fields matched;
- provider metadata and unsupported/not-managed fields were present;
- `fallback_used=false` for every accepted action;
- no task/default proxy override was accepted.

### Crawl Trigger Matrix

- HTTP manual run completed with real platform output;
- scheduler run completed after restart;
- monitor CLI run completed;
- each run reached Runner, platform core, and launch-owned CDP;
- all three retain the same stable environment digest and account reference;
- trigger sources are exactly `manual`, `scheduler`, and `cli_manual`, with
  separate safe run/result references;
- no run used generic Profile or default network.

### Runtime Authority, Redaction, And Safety

- safe result browser source is explicit or Playwright-bundled, never local
  diagnostic auto-detection;
- safe result Profile reference matches the account and stable digest;
- safe result proxy policy is account-bound and effect proof passed;
- safe result provider mode is launch-owned, mismatch evidence is empty, and
  `fallback_used=false`;
- parent accepted a matching child result before output ingest;
- raw Cookie, proxy credential, Profile path, internal plan, CDP endpoint,
  command line, and server path were absent from stored evidence, UI/API,
  run summaries, and committed docs;
- Cookie-account evidence ends after validation. It does not claim raw Cookie
  argv retirement or a Cookie-account crawl;
- filled evidence remained outside Git;
- all real actions were serial and bounded.

### Chronology And Internal Consistency

- `baseline.commit` equals the explicit `RUNTIME_COMMIT` taken from the
  deployed checkout's full `git rev-parse HEAD` value;
- `main@27389a8` is only this packet's historical Task 1 start baseline. After
  the checker commit merges, operators must use the later commit actually
  deployed and must not reuse `27389a8` as an implied acceptance default;
- template creation occurs no later than the recorded run-window start; every
  action timestamp falls inside the run window, and restart occurs between
  pre-restart and post-restart actions;
- resolution/attempt references are unique per action;
- the same stable environment digest appears for QR Profile check and all
  three QR-account crawl triggers;
- QR environment lock timestamp is unchanged across restart;
- exactly one manual, one scheduler, and one CLI trigger are present;
- each real crawl records terminal status in 1-300 seconds, exactly one page,
  and 1-10 accepted items;
- operator and independent reviewer attestations are non-placeholder.

The checker rejects placeholder references, forbidden sensitive keys, raw
Windows/Linux paths, Cookie/header-like values, proxy URLs/credentials,
tokens, passwords, command lines, internal plan/result payloads, and incomplete
required booleans. It validates the internal consistency above but explicitly
reports that external truth still depends on operator observation and reviewer
cross-check of the redacted record references.

## Acceptance Gate

Phase 5.1 passes only when the redacted checker returns success for one real
Docker/Linux workflow and all required groups above. The gate must include real
QR login, real Cookie validation, post-restart Profile reuse, real bound-proxy
browser egress, real platform crawl through manual/scheduler/CLI triggers,
launch-owned CDP, stable requested/effective and runtime-authority evidence,
and `fallback_used=false`. Raw process inspection is not required proof.

Automated `485` tests, the existing lightweight server-like script, Docker
configuration parsing, local Chrome/Edge, a browser launch without platform
work, or a partially filled evidence file do not close this gate.

## Rollback And Recovery

- Checker/docs changes roll back by reverting this packet's commit.
- Stop the scheduler and service/container before investigating a failed real
  checkpoint.
- Preserve the dedicated acceptance Profile and database until restart/failure
  evidence is understood; do not auto-delete the only usable Profile.
- Remove dedicated acceptance data only after the operator confirms evidence
  capture is complete and no diagnosis/retry is needed.
- A failed or interrupted checkpoint remains incomplete and is safe to rerun
  serially after the owning defect or environment gate is resolved.

## Stop Conditions

Stop and keep Phase 5.1 open when:

- the deployed commit differs from the recorded baseline;
- Docker/Linux, server browser, dedicated account, proxy, or probe is absent;
- a required platform verification needs operator action that has not occurred;
- a runtime action uses or needs a second browser/Profile/proxy/identity
  authority;
- proxy effect is unproved or mismatched;
- Profile login state does not survive restart;
- any manual/scheduler/CLI run lacks a successful bound result before ingest;
- any accepted result has `fallback_used=true` or uses generic Profile,
  process/default proxy, default network, connect-existing CDP, or standard
  fallback;
- evidence contains a secret, raw path, command, endpoint, or runtime payload;
- product code would need to change inside this acceptance packet.
