# Phase 5.1B Account Identity Generation And Validation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:executing-plans and superpowers:test-driven-development. Complete
> this packet in order, then use an independent read-only reviewer on the full
> diff before integration.

**Goal:** Generate and persist one deterministic, explainable browser identity
for each newly created platform account, validate it fail-closed, and expose
only safe account-environment controls and summaries.

**Architecture:** Add a focused, mostly pure `account_identity` module that
owns the versioned catalog, HMAC selection, exact expansion, validation, and
test-side-effect gate definitions. `database.py` remains the persistence
authority: after a new account receives its database ID and `profile_key`, it
calls the generator once and writes only the generator-owned columns. Existing
accounts are not backfilled or regenerated. Phase 5.1C will own later state
transitions, locks, reset/re-login, and regeneration.

**Tech Stack:** Python 3.11, SQLite, FastAPI, existing static monitor UI,
pytest, HMAC-SHA256 from the Python standard library.

## Confirmed Implementation Decisions

1. **Seed authority:** pure generator tests pass an explicit salt. Normal
   runtime first accepts the UTF-8 bytes of
   `MONITOR_ACCOUNT_IDENTITY_SEED_SALT` when explicitly configured. Otherwise,
   decode the existing URL-safe-base64 Fernet deployment key to its 32 raw
   bytes and derive the generator salt with this exact Python expression:
   `hmac.new(deployment_key_bytes,
   b"MediaCrawler/account-identity/seed/v1",
   hashlib.sha256).digest()`. For every HMAC in this packet and
   `ACCOUNT_ENVIRONMENT.md`, the first tuple element is the HMAC key and the
   serialized canonical input is the message. The resulting 32 bytes are the
   `seed_salt` key passed as the first argument to the documented selection and
   fingerprint HMACs. The raw deployment key/salt is never stored in SQLite,
   returned by an API, logged, or accepted from a request payload. Backup and
   restore must preserve either the explicit environment salt or the existing
   deployment key; changing that authority is an identity migration and later
   reset/re-login event, not an in-place regeneration.
2. **New-account timing:** `save_social_account` inserts the row first so the
   stable account ID exists, derives `profile_key`, then generates and validates
   the identity and persists it as `identity_state='generated'`. Phase 5.1C
   performs the explicit persisted `generated -> validated` transition before
   login launch.
3. **Legacy boundary:** Phase 5.1B generates only on initial INSERT. Every
   UPDATE, including a draft account name, proxy, or notes update, preserves
   the current identity columns and never regenerates. Phase 5.1C supplies the
   explicit generation/regeneration command and transition rules.
4. **Region authority:** `proxy_region_snapshot` is a customer-safe account
   policy snapshot, not proxy discovery. New account creation defaults to
   `CN_MAINLAND`; an administrator may choose another accepted bucket before
   first save and is responsible for matching it to the selected proxy because
   the current proxy table has no region column. If a `proxy_id` is provided,
   validation proves that record exists. Phase 5.1B does not infer geography
   from credentials or URLs; Phase 5.1D separately proves the effective proxy
   transport and records requested/effective evidence.
5. **UI boundary:** ordinary creation needs no identity choice. A collapsed
   advanced section shows only safe region and template-family selects. They
   are active only before the first save; generated fields are read-only and
   never submitted by the browser.
6. **API boundary:** unknown/direct identity field payloads do not become
   persistence inputs. Only new-account `proxy_region_snapshot` and
   `identity_template_family` influence generation. All current social-account
   list/detail/save/check routes remain administrator-only; there is no normal
   user account-resource endpoint. Their customer-safe account payload may
   include `identity_state`, template, region, platform, dimensions, locale,
   timezone, device flags, and generator name/version metadata. Every response
   omits `fingerprint_seed`, `identity_runtime_snapshot_json`, Cookie material,
   proxy credentials, and raw Profile/runtime paths. Phase 5.1D may later add a
   separately redacted parsed runtime summary rather than exposing stored JSON.
7. **Transaction/filesystem boundary:** generation and validation run inside
   the same SQLite transaction as the new account INSERT and bounded identity
   UPDATE. `resolve_account_profile_path` validates/derives a path string but
   does not create the directory. Profile directory creation remains deferred
   to a later browser-login operation after commit, so a generation failure
   rolls back the complete account row and leaves no new Profile directory.
8. **Template-family mapping:** `auto` keeps every candidate for the selected
   region. `windows_chrome_desktop` keeps candidates whose catalog family is
   Windows desktop (`CN_WIN_CHROME_1920`, `CN_WIN_CHROME_1536`,
   `HK_DESKTOP_CHROME`, `SG_DESKTOP_CHROME`), after region filtering.
   `mac_chrome_desktop` keeps only `CN_MAC_CHROME_1440`, and
   `android_chrome` keeps only `CN_ANDROID_CHROME`. Region filtering happens
   first; therefore HK/SG plus Mac/Android has no candidate and fails closed.
9. **Region bundles:** V1 validation treats region as declared policy evidence,
   not measured geolocation. `CN_MAINLAND` requires
   `environment_region=CN_MAINLAND`, `Asia/Shanghai`, `zh-CN`, and
   `zh-CN,zh;q=0.9`; `HK` requires `environment_region=HK`,
   `Asia/Hong_Kong`, `zh-HK`, and `zh-HK,zh;q=0.9,en;q=0.8`; `SG` requires
   `environment_region=SG`, `Asia/Singapore`, `en-SG`, and
   `en-SG,en;q=0.9,zh;q=0.7`. The catalog row supplies the device fields. The
   administrator-declared `proxy_region_snapshot` must equal the bundle key.
   Phase 5.1D proves that the declared proxy is the effective transport; Phase
   5.1B does not claim endpoint geolocation.
