**Goal:** Make the persisted account identity lifecycle authoritative across
QR login, visible-browser maintenance, Cookie/Profile validation, environment
changes, reset/re-login, and audit without changing browser launch settings.

**Architecture:** Keep deterministic generation/validation pure in
`account_identity.py` and keep SQLite plus audit writes authoritative in
`database.py`. Add one transactional lifecycle service surface for prepare,
success, failure, pre-login reconfiguration, locked-change marking, and
administrator reset. Existing router/account-check paths call these functions;
they do not write identity state independently. Phase 5.1D remains the owner of
provider launch options, runtime probes, snapshots, and effective proxy proof.

**Tech Stack:** Python 3.11, SQLite, FastAPI, existing static monitor UI,
pytest.

## Confirmed Implementation Decisions

1. **One state authority:** only database lifecycle functions mutate
   `identity_state`, `requires_relogin`, and browser-environment lock fields.
   Routes and account checks call them and consume returned account rows.
2. **Prepare semantics:** a `draft` account is generated explicitly when an
   administrator starts login/check; `generated` is validated; `validated`
   enters `login_in_progress`. A valid `locked`/`active` account may enter
   maintenance login with the same identity. `requires_relogin` and
   `resetting` reject ordinary login; another `login_in_progress` rejects
   concurrent login.
3. **Success semantics:** QR success is not enough by itself. The existing
   account-level verification must pass. Cookie/Profile check success locks the
   same persisted identity with reason `qrcode_login_success`,
   `cookie_validation_success`, or `profile_validation_success`, records
   `identity_locked`, then records `identity_activated` and leaves final state
   `active`.
4. **Failure semantics:** a terminal launch/check failure or cancelled QR
   session keeps generated fields and previous Profile/Cookie data and records
   `identity_launch_failed`. If lock timestamp/reason are still present, the
   attempt began from locked/active maintenance and failure restores `active`
   without changing the existing lock. Otherwise failure performs
   `login_in_progress -> validated`. Pending QR/manual verification states
   remain `login_in_progress`.
5. **Change semantics:** in `draft`, `generated`, or `validated`, a safe
   region/family/proxy change transitions through `draft -> generated ->
   validated`. During `login_in_progress` it is rejected. In `locked` or
   `active`, the attempted new values are not applied; the current locked
   identity/proxy remain unchanged and state becomes `requires_relogin` with an
   audit event.
6. **Reset boundary:** the explicit administrator reset accepts the desired
   safe proxy/region/family, records `identity_reset_requested`, checks no
   active account/run lock or login, enters `resetting`, clears generated
   identity/lock/runtime-snapshot metadata, applies the safe proxy policy,
   records `identity_reset_completed`, regenerates and validates, and ends in
   `validated` plus account pool status `standby`. It preserves account ID,
   `profile_key`, legacy path metadata, encrypted Cookie, platform identity,
   and Profile files. A later login/check must succeed before `active`.
7. **Audit boundary:** lifecycle audit detail contains actor/system source,
   trigger, account/workspace/platform, template, old/new state, old/new safe
   region, safe proxy IDs, reason code, and no secret or raw path.
8. **CR-113 boundary:** QR draft creation forwards only the already accepted
   `proxy_region_snapshot` and `identity_template_family`; it does not reopen
   Phase 5.1B or add field-level editing.
9. **Login-state mapping:** `preparing`, `waiting_qrcode`, `waiting_scan`,
   `waiting_confirm`, and `needs_verification` keep identity state
   `login_in_progress`. QR status `success` still waits for account-level
   verification. `qrcode_failed`, `timeout`, `platform_error`, explicit QR
   session deletion, and synchronous browser-start failure record
   `identity_launch_failed`; they restore `active` when existing lock metadata
   proves a maintenance attempt, otherwise they recover to `validated`.
10. **Stale ownership:** a persisted `login_in_progress` is never silently
    treated as active after restart. QR session deletion and terminal status
    recover it. Visible-browser validation explicitly continues the prepared
    state after the operator closes the window. A new QR/visible-browser start
    still rejects an existing `login_in_progress`; no timeout guess or second
    login authority is added.

## CR-113 Regression Contract

**Type:** regression fix linked to CR-047 / completed Phase 5.1B.

**Observed cause:** `startLoginSessionForDraft()` submits the accepted safe
`proxy_region_snapshot` and `identity_template_family` to
`POST /login-sessions`, but `create_platform_login_session()` currently builds
the `create_draft_social_account()` payload from only name, platform, proxy ID,
and notes. The route therefore drops the two safe choices and Phase 5.1B uses
CN/auto defaults.

**Fix/acceptance:** add only those two existing safe keys to the draft creation
payload. A route test captures the `create_draft_social_account()` argument and
proves exact forwarding. Unknown/generated identity fields remain absent; saved
account, existing-account QR, and field-level ownership behavior stay unchanged.
Task 8 records this contract in `CHANGE_REQUESTS.md`, `TASKS.md`, tests,
traceability, and results without changing Phase 5.1B historical status.

## Lifecycle Function Contract

`account_identity.py` adds constants for all eight states plus locked/pending
sets. `database.py` adds these exact public functions:

```python
prepare_social_account_identity_login(
    account_id: int,
    *,
    trigger_source: str,
    user_id: int | None = None,
    allow_prepared_validation: bool = False,
) -> dict[str, Any]

complete_social_account_identity_login(
    account_id: int,
    *,
    ok: bool,
    trigger_source: str,
    lock_reason: str = "",
    failure_reason: str = "",
    user_id: int | None = None,
) -> dict[str, Any]

apply_social_account_identity_configuration(
    account_id: int,
    *,
    proxy_id: int | None,
    proxy_region_snapshot: str,
    template_family: str,
    trigger_source: str,
    user_id: int | None = None,
) -> dict[str, Any]

reset_social_account_identity(
    account_id: int,
    *,
    proxy_id: int | None,
    proxy_region_snapshot: str,
    template_family: str,
    trigger_source: str = "admin_reset",
    user_id: int | None = None,
) -> dict[str, Any]
```

Internal helpers own bounded identity writes, clearing, transitions, and audit;
callers never issue lifecycle SQL.

`allow_prepared_validation=False` is the concurrency-safe default: an existing
`login_in_progress` raises a conflict. `True` means the caller is continuing
account verification for the already prepared QR/visible-browser operation;
the function requires the current state to be exactly `login_in_progress`,
revalidates the persisted identity, and performs no second transition or audit.
`check_social_account_login(identity_prepared=True)` maps directly to this
mode. The administrator check-login route may set it only when the persisted
account is already `login_in_progress`, allowing post-visible-window validation;
new QR/visible-browser starts always use the default and remain mutually
exclusive.

## Audit Contract

Every identity event uses the existing `audit_logs` row. `user_id` stores the
actor; a system transition uses NULL. `details_json` has this exact safe shape:

```json
{
  "trigger_source": "qrcode_login",
  "account_id": 41,
  "workspace_id": 1,
  "platform": "dy",
  "identity_template": "CN_WIN_CHROME_1920",
  "old_identity_state": "login_in_progress",
  "new_identity_state": "locked",
  "old_proxy_region_snapshot": "CN_MAINLAND",
  "new_proxy_region_snapshot": "CN_MAINLAND",
  "old_proxy_id": 2,
  "new_proxy_id": 2,
  "reason": "qrcode_login_success"
}
```

The identity audit helper has an explicit allowlist for only these keys. It
never accepts `fingerprint_seed`, generated UA/device fields, Cookie material,
proxy URL/credentials, Profile/runtime path, runtime snapshot JSON, CDP/noVNC
data, or command lines. Tests parse stored JSON and assert exact keys.

## Reset Field Contract

The reset helper explicitly clears every `GENERATOR_OWNED_FIELDS` column using
the Phase 5.1A empty representation: text fields to `''`, dimensions/scale to
SQL NULL, booleans to `0`; it also clears
`browser_environment_locked_at`, `browser_environment_lock_reason`, and
`identity_runtime_snapshot_json`, and sets `requires_relogin=0`. It does not
clear `profile_key`, legacy `profile_path`, `cookies_encrypted`, platform
identity fields, account ID, or account/run lock fields. The same transaction
then applies the safe target proxy, regenerates, validates, and finishes
`identity_state='validated'`, `status='standby'`.

Before any reset write, the helper rejects when
`identity_state='login_in_progress'` or `locked_by_run_id IS NOT NULL`. It does
not guess whether `lock_expires_at` is stale and has no force option; existing
run/lock recovery must clear stale ownership first. It raises the named safe
reason `account_identity_reset_blocked`. The administrator route maps this and
`account_identity_requires_relogin`/concurrent-login conflicts to HTTP 409;
validation/input errors remain HTTP 400. No partial state/audit write commits.

## Existing Integration Points

- `monitor.create_platform_login_session` is the existing
  `POST /login-sessions` route. Its no-`account_id` branch calls
  `create_draft_social_account`; CR-113 extends that existing payload.
- `monitor.create_platform_login_session` prepares after account resolution
  and before `_login_browser_command_for_payload`/Playwright startup.
- `monitor.platform_login_browser` prepares an account-bound visible-browser
  flow before command/process startup and recovers synchronous failure.
- `monitor._verify_successful_login_session` and
  `_reconcile_login_session_with_account_check` already call
  `check_social_account_login`; both pass `identity_prepared=True`.
- `account_check.check_social_account_login` changes signature to
  `(..., allow_draft=False, identity_prepared=False, actor_id=None)`. It calls
  prepare unless already owned, then calls complete exactly once after the
  Cookie/Profile result.
- The administrator single/bulk check routes inspect only persisted
  `identity_state`; when it is `login_in_progress`, they pass
  `identity_prepared=True` to continue visible-browser validation. They do not
  set this flag for any other state.
- `monitor.remove_login_session` and terminal session-status handling recover
  the account identity before deleting/returning the session.
- `monitor.update_social_account` passes safe configuration requests to the
  database authority; it does not mutate generated fields itself.

## UI/API Data Contract

Existing administrator-only `/social-accounts` responses already retain safe
`identity_state`, `requires_relogin`, template, region, browser platform,
lock reason/time, and proxy ID while redacting seed/snapshot/secrets/paths.
The reset endpoint returns the same `_customer_view_social_account` shape.
`account_detail_summary` adds an `账号环境` item; a new
`social_account_identity_status` notice shows the safe state/consequence; and
`account_identity_change_button` plus `account_identity_reset_button` control
the explicit flow. No new normal-user endpoint or debug payload is added.

`prepare_social_account_identity_login` is the API source of truth for blocked
login: `requires_relogin` raises `account_identity_requires_relogin`,
`resetting` or concurrent start raises a conflict, and account-bound QR/
visible-browser routes return HTTP 409 with customer-safe text. The UI mirrors
this by disabling QR start, visible-browser start, Cookie save/validation, and
single/bulk check actions for `requires_relogin` or `resetting`; it leaves the
reset action enabled and displays the reset/re-login consequence. Frontend
blocking is not the security boundary.
